# Стратегія тестування

Стратег: Артем Бутирін. Деталі прогону тестів і звіт покриття — у [README.md](README.md).

## Поточний статус

Піраміда зараз **плоска знизу**: є лише модульний рівень, і він уже в CI.

| Рівень (V-модель) | Зараз | Інструменти |
| ----------------- | ----- | ----------- |
| Модульний | Є: `organization`, `event` | JUnit 5, Mockito, AssertJ, фікстури `TestFixtures` |
| Інтеграційний | Немає | плануємо MockMvc / Testcontainers Postgres |
| Системний | Немає | наскрізний гість → каталог orgs → події |
| Приймальний | Немає | демо за US з Lab 2 |

Запуск: `./mvnw test`. Тести в `src/test/java/` (стандарт Maven). Фронт (`web-src`) модульних тестів не має — перевіряється збіркою `tsc` + Vite в CI.

## Покриття

Знімок JaCoCo: [`coverage/jacoco/`](coverage/jacoco/index.html) (колонки LINE у `jacoco.csv`).

- **Рядки: 45.1%** (185 / 410). Ворота в `pom.xml` (`jacoco-check`): **5%** рядків — тимчасовий нижній поріг, щоб пайплайн ловив регресію «тести зникли», а не блокував ріст коду.
- Добре покрито домен `OrganizationService` і частину `EventService` / `Event` (пошук, slug, модерація, дедуп).
- **Не покрито навмисно зараз:** HTTP-контролери (`OrganizationController`, `EventController`, …), `calendar` (експорт `.ics` / Google), `GlobalExceptionHandler`, in-memory event-репозиторій, React UI, Auth. Модульні тести ізолюють сервіси; контролери й календар дадуть цінність на інтеграційному рівні, а не дублюванням моків.

## План наступних рівнів

1. **Інтеграційні (архітектура → стики):** Spring `MockMvc` на `GET /api/v1/organizations` і створення події; пізніше — Testcontainers PostgreSQL замість in-memory, коли сервіс підключать до БД (зараз дані в пам’яті).
2. **Системні (система як чорна скриня):** один сценарій: відкрити UI → список організацій з живого API (proxy `/api`). Без повного E2E-фреймворку до стабілізації Auth.
3. **Приймальні (вимоги):** чекліст демо за US/FR Lab 2 (каталог, модерація, дедуп) на лабораторній, не в CI.

Пропорція-ціль піраміди: багато модульних на кожен PR; мало інтеграційних на merge; одиниці системних перед демо.

## Продуктивність, безпека, property-based

- **Продуктивність:** окремих тестів немає; NFR з Lab 2 перевірятимемо після деплою в Minikube, не в модульному наборі.
- **Безпека:** не дублюємо SAST тут — SpotBugs + find-sec-bugs і eslint-plugin-security уже в Lab 5 (`lint.yml`). Динамічні тести доступу (401/403) — разом з інтеграційним шаром Auth.
- **Property-based:** не використовуємо (jqwik / fast-check — кандидат на бонус, не на цей спринт).

## CI/CD (shift-left)

На кожен push/PR у `main` job **Build and Test Backend** у [`.github/workflows/ci.yml`](.github/workflows/ci.yml):

1. компіляція тестів;
2. `./mvnw test` — Surefire + звіт JaCoCo + **падає, якщо покриття рядків < 5%**;
3. package;
4. summary (кількість тестів, % рядків) і артефакт `test-reports` (7 днів).

Frontend job збирає SPA, але тестів не ганяє. Merge в `main` лише з зеленим CI і approve (§5 статуту). Локально автор ганяє `./mvnw test` перед PR.

Коли покриття домену стабілізується вище ~40%, поріг `jacoco-check` піднімаємо ближче до факту — щоб ворота знову щось ловили.

## Бонуси

3. **Ворота покриття в CI.** `jacoco-check` у `pom.xml` (мінімум **5%** рядків) виконується на кожен PR у job `Build and Test Backend`. Поріг низький навмисно: фактичне покриття ~45%, але кодова база ще росте (календар, Auth, контролери); 5% ловить зникнення набору тестів, не блокує новий код. Підніматимемо, коли покриття домену стабілізується. Доказ: зелений прогін `ci.yml` на PR з тестами.

1–2 (мутації, property-based) у цьому сприті не робимо.
