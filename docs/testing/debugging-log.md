## Причина

У фільтрі нижньої межі вибірки включна межа замінена на виключну:

```diff
-                .filter(e -> !e.startsAt().isBefore(lowerBound))   // ≥ межі
+                .filter(e -> e.startsAt().isAfter(lowerBound))     // > межі
```

`!isBefore` і `isAfter` відрізняються **рівно одним випадком — коли значення збігаються**. Подія, що починається точно на нижній межі діапазону, зникає з каталогу.

**Діагностика.** Точка зупину на рядку 47 з умовою `e.startsAt().isEqual(lowerBound)`. У вікні змінних обидва значення однакові — `2026-10-21T13:00+03:00`. Через Evaluate Expression перевірено обидва варіанти на тих самих даних:

```java
e.startsAt().isAfter(lowerBound)    // false → подія відсіюється
!e.startsAt().isBefore(lowerBound)  // true  → подія проходить
```

**Наслідок для користувача.** Порушується FR-038: каталог опублікованих майбутніх подій. Найпомітніше, коли клієнт сам задає `from` — фільтр «події від 12 березня» не покаже подію, що починається 12 березня опівночі.

**Чому це підступна помилка:**

- компілятор мовчить — обидва вирази валідні й повертають `boolean`;
- на рев'ю `isAfter` читається навіть природніше за подвійне заперечення `!isBefore`;
- ручне клікання її не виявить: треба натрапити на подію, що починається точно на введеній межі.

## Виправлення

Повернуто строгу поведінку меж `[from, to)` — нижня включна, верхня виключна. Коміт `8bcdc6a`, одна зміна в одному рядку. Прогін після виправлення: `Tests run: 44, Failures: 0` — повернення до базового стану.

**Про регресійний тест.** Помилку спіймав **наявний** граничний тест `boundariesAreInclusiveLowerExclusiveUpper` (`EventServiceTest.java:78`), написаний командою на Лабораторній 6 від вимоги про межі. Додавати новий тест на цей самий випадок не було потреби.

Проте під час розбору виявлено **прогалину**: друга форма тієї самої помилки не покрита жодним тестом. Є тест для межі «зараз» і тест для `from` у минулому, але немає випадку, коли клієнт передає `from` у майбутньому, а подія починається точно в цей момент. Саме цей сценарій найчастіше трапляється в реальному використанні.

## Урок

**Помилки живуть на межах.** `>` проти `>=`, `isAfter` проти `!isBefore` — найдешевший спосіб зламати систему непомітно для всіх автоматичних перевірок, крім тесту, написаного саме на межу.

**Сто відсотків покриття не означає сто відсотків перевірки.** У методу `digest` п'ять тестів, і чотири з них виконували зламаний рядок, лишаючись зеленими:

| Тест `digest` | Результат |
| ---------------------------------------- | --------- |
| `boundariesAreInclusiveLowerExclusiveUpper` | ❌ |
| `onlyPublishedUpcomingSortedByStart` | ✅ |
| `pastFromIsClampedToNow` | ✅ |
| `filtersByOrganization` | ✅ |
| `emptyRangeIsRejected` | ✅ |

Покриття показує, що рядок **виконався**, а не що його поведінку **перевірили**. Відсоток покриття цього рядка був стовідсотковим і до поломки, і після неї.

**Назва тесту заощаджує час налагодження.** «Межі: подія рівно «зараз» входить, подія рівно о `to` — ні» одразу повідомила, що саме зламано, — не довелося читати код тесту, щоб зрозуміти суть збою.

**Що робити інакше.** Для кожного діапазону писати окремий тест на кожну межу й прямо називати в тесті, яка з них включна. Там, де межі задає клієнт, перевіряти обидва джерела межі — і значення за замовчуванням, і передане параметром.
