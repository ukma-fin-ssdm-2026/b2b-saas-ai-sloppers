# Атрибути якості API

Кожна ціль нижче має три частини: **число**, **спосіб його виміряти** і **умову, за якої ціль вважається невиконаною**.

Джерела: [api-design.md](api-design.md), [non-functional-requirements.md](../requirements/non-functional-requirements.md), [traceability-matrix.md](../architecture/traceability-matrix.md).

Межа вимірювання цього семестру: відповіді — заглушки в пам'яті процесу (`OrganizationService`), без PostgreSQL. Числа лишаються цільовими, прогін повторюємо після під'єднання бази.

## Продуктивність

**Ціль:** 95-й перцентиль часу відповіді `GET /api/v1/organizations` < 500 мс за 50 одночасних користувачів; частка відповідей `5xx` < 1% за 100 одночасних користувачів.

**Умова провалу:** p95 ≥ 500 мс або хоча б один таймаут у п'ятихвилинному прогоні; частка `5xx` ≥ 1% на піковому навантаженні.

**Реалізація:**
- Пагінація зі зсувом, розмір сторінки обмежено зверху 100 елементами (`limit` > 100 → `400`, а не мовчазне обрізання).
- Скрейпінг соцмереж винесено з шляху HTTP-запиту у фоновий воркер ([ADR-001](../architecture/decisions/ADR-001-architectural-style.md)).
- Індекси під запити каталогу за `name` і `slug` (після під'єднання PostgreSQL).
- Кешування каталогу (заплановано).

**Вимірювання:** навантажувальний тест k6, 5 хвилин рівного навантаження, два профілі — 50 і 100 віртуальних користувачів.

**Пов'язані вимоги:** NFR-001, NFR-002.

## Безпека

**Ціль:** невалідний вхід завжди отримує `400` з кодом помилки й переліком полів; 100% операцій запису оголошують `bearerAuth`, `401` і `403`; жодного витоку внутрішніх деталей у тілі відповіді.

**Умова провалу:** хоча б один невалідний вхід дає `200`, `5xx` або `400` без `details`; хоча б одна операція запису без `security` у специфікації; хоча б одна відповідь містить назву класу, стектрейс, SQL або шлях файлу.

**Реалізація:**
- Bean Validation на всіх параметрах і полях тіла; єдиний `GlobalExceptionHandler` на межі API.
- Єдиний каркас помилки: `code`, `message`, `details`, `requestId`; назви класів і стектрейси назовні не потрапляють, `500` повертає лише загальне повідомлення.
- JWT Bearer для операцій запису (заплановано; у заглушках не перевіряється, але вже є частиною контракту).
- Обмеження частоти запитів (заплановано).
- Лише HTTPS у продакшні, секрети — у K8s Secrets.

**Вимірювання:** набір із 31 невалідного запиту через Swagger UI (розділ «Перевірка валідації»); перегляд `openapi-generated.yaml` на наявність `security` і кодів `401`/`403`; grep по тілах відповідей на `Exception`, `at ua.edu.ukma`, `SQL`.

**Пов'язані вимоги:** NFR-009, NFR-010, NFR-012.

## Надійність

**Ціль:** доступність ≥ 99% за тиждень; 100% відповідей `4xx` і `5xx` містять `requestId`.

**Умова провалу:** понад 100 хвилин сумарного простою за 7 днів; хоча б одна помилка без `requestId`; падіння процесу на невалідному вході.

**Реалізація:**
- Кінцева точка перевірки стану `/actuator/health`.
- Обробка всіх помилок через `GlobalExceptionHandler`, зокрема зламаного JSON, невідомого маршруту й невірного методу — процес не падає.
- `requestId` у кожній помилці для пошуку в логах.
- Репліка PostgreSQL у Minikube з відновленням ≤ 30 с (заплановано, рівень розгортання).

**Вимірювання:** зовнішній моніторинг опитує `/actuator/health` щохвилини; негативні тести перевіряють наявність `requestId` у кожній помилці.

**Пов'язані вимоги:** NFR-003, NFR-004.

## Супроводжуваність документації

**Ціль:** `openapi-generated.yaml` відтворюється з коду однією командою і збігається з закоміченою версією байт-у-байт; 100% кінцевих точок мають `summary`, опис, приклад і перелік кодів помилок.

**Умова провалу:** згенерований файл відрізняється від закоміченого, тобто його правили руками; хоча б одна точка без `summary` або без прикладу; несумісна зміна всередині `/api/v1`.

**Реалізація:**
- Code-First: специфікація генерується springdoc з анотацій, вручну не редагується.
- Спільні `components/responses` замість дублювання описів помилок у кожній точці.
- Мажорна версія в шляху (`/api/v1`); несумісні зміни — лише у `v2`.

**Вимірювання:** перегенерація специфікації й `git diff --exit-code` у CI; чекліст повноти анотацій (розділ нижче).

**Пов'язані вимоги:** NFR-012.

## Аналіз компромісів

| Атрибут | Компроміс | Вплив | Пом'якшення |
| ------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------- |
| Безпека (валідація на межі API) | додаткова затримка на кожен запит | мінімальний, одиниці мілісекунд | валідація лише на межі, без повторних перевірок у шарах нижче |
| Продуктивність (пагінація, ліміт 100) | за один запит не можна отримати весь каталог | клієнту потрібно кілька запитів | більший ліміт для адміністративних сценаріїв |
| Передбачуваність (`limit=101` → `400`) | клієнт отримує помилку замість часткового результату | зайвий цикл виправлення на боці клієнта | межа описана в специфікації як `maximum: 100` з прикладом |
| Безпека (приховані деталі помилок) | розробнику складніше діагностувати збій | повільніший розбір інцидентів | `requestId` у кожній відповіді, повні деталі лише в логах |
| Надійність (дедуплікація в БД) | логіка розділена між кодом і схемою бази | частину правил не видно з коду сервісу | обмеження задокументовані в `data-model.md` і покриті тестами |
| Code-First (генерація зі Spring) | специфікація залежить від фреймворку й анотацій | ризик «розповзання» контракту при рефакторингу | перевірка `git diff --exit-code` на згенерованому файлі в CI |

## Сценарії атрибутів якості

Сценарії записані в шестичастинному форматі: джерело — стимул — артефакт — середовище — відповідь — міра відповіді.

### QS-01 · Продуктивність каталогу під піковим навантаженням

| Частина | Значення |
| ------------------ | ------------------------------------------------------------------------------------- |
| **Джерело** | Студенти, які відкривають каталог організацій |
| **Стимул** | 100 одночасних `GET /api/v1/organizations` з різними `q`, `limit`, `offset` |
| **Артефакт** | `OrganizationController`, `OrganizationService`, сховище даних |
| **Середовище** | Штатна робота, піковий день після розсилки анонсу; фоновий скрейпер виконує цикл збору |
| **Відповідь** | Сервіс обробляє запити на читання; фоновий збір не блокує обробку HTTP-запитів |
| **Міра відповіді** | p95 < 500 мс при 50 користувачах; частка `5xx` < 1% при 100 користувачах за 5 хвилин |

### QS-02 · Невалідний вхід не доходить до домену

| Частина | Значення |
| ------------------ | ------------------------------------------------------------------------------------------ |
| **Джерело** | Клієнт із помилкою в коді або зловмисник, який перебирає входи |
| **Стимул** | Запит зі зламаним JSON, `limit=1000`, `slug` із пробілами, `id` не у форматі UUID |
| **Артефакт** | Bean Validation на межі API, `GlobalExceptionHandler` |
| **Середовище** | Штатна робота, будь-яка кінцева точка |
| **Відповідь** | Запит відхиляється на межі з `400`, перелік порушених полів у `details`, `requestId` у тілі |
| **Міра відповіді** | 100% з 31 негативного входу дають `400`; 0 відповідей `5xx`; 0 витоків стектрейсів |

### QS-03 · Відмова зовнішнього джерела не впливає на API

| Частина | Значення |
| ------------------ | -------------------------------------------------------------------------------------- |
| **Джерело** | Instagram як зовнішнє джерело |
| **Стимул** | Джерело недоступне або відповідає повільно під час циклу збору |
| **Артефакт** | Scraper Worker, кінцеві точки каталогу |
| **Середовище** | Штатна робота; користувачі одночасно читають каталог |
| **Відповідь** | Воркер робить до 3 повторних спроб, зберігає статус помилки й переходить до інших джерел; API віддає раніше зібрані дані |
| **Міра відповіді** | 0 помилок `5xx` на кінцевих точках каталогу; 100% решти джерел опрацьовано в тому ж циклі |

## Патерни стійкості API

| Патерн | Де застосовуємо | Стан |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------- |
| Валідація на межі | Усі параметри й тіла запитів; невалідний вхід не доходить до сервісного шару | ✅ реалізовано |
| Єдина обробка помилок | `GlobalExceptionHandler` перехоплює і доменні, і фреймворкові помилки; процес не падає на невідомому маршруті | ✅ реалізовано |
| Обмеження розміру відповіді | `limit` ≤ 100: один запит не може «витягнути» весь каталог | ✅ реалізовано |
| Ідемпотентність | `GET`, `PATCH` з тим самим тілом і `DELETE` повторно дають той самий стан; повторний `DELETE` → `404` | ✅ реалізовано |
| Таймаути на зовнішні виклики | Scraper Worker → Instagram: обмеження часу очікування | ⏳ заплановано |
| Повторні спроби з паузою | До 3 спроб на джерело, помилка одного джерела не зупиняє цикл (NFR-007) | ⏳ заплановано |
| Ізоляція повільних операцій | Скрейпінг винесено з HTTP-шляху у фоновий воркер ([ADR-001](../architecture/decisions/ADR-001-architectural-style.md)) | ✅ архітектурно |
| Обмеження частоти запитів | Захист від зловживання кінцевими точками запису | ⏳ заплановано |
| Перевірка стану | `/actuator/health` для моніторингу й перезапуску пода | ⏳ заплановано |
| Деградація замість відмови | Якщо збір не спрацював, каталог віддає раніше зібрані події, а не помилку | ✅ за побудовою |

Свідомо **не** застосовуємо circuit breaker: єдина зовнішня залежність викликається фоновим воркером за розкладом, не в шляху запиту користувача, тож розмикання кола нічого б не врятувало. Достатньо таймауту й повторних спроб.

## Кешування відповідей API

| Рішення | Де | Навіщо |
| ------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------------ |
| `Cache-Control: public, max-age=60` | `GET /organizations`, `GET /organizations/{id}` | Каталог змінюється рідко, а читають його часто; знімає пік з бази |
| `ETag` + `If-None-Match` → `304` | ті самі точки | Клієнт не перекачує незмінений список; економія трафіку на мобільних |
| `Cache-Control: no-store` | усі операції запису й майбутні приватні дані | Відповіді з контактами й токенами не мають потрапляти в кеш проксі |
| Інвалідація за зміною | `POST`, `PATCH`, `DELETE` | Після запису `ETag` ресурсу змінюється, клієнт отримує свіжу версію |

**Умова провалу для кешування:** клієнт отримує застарілу організацію більш ніж через 60 секунд після її зміни, або відповідь із приватними даними має заголовок, що дозволяє її кешувати.

**Компроміс:** 60 секунд вікна застарілості в обмін на зменшення навантаження. Для каталогу, який оновлюють кілька разів на тиждень, це прийнятно; для черги модерації кешування вимкнено повністю, бо голова має бачити зміни одразу.

Стан: заголовки кешування ще не реалізовані, це наступний крок після під'єднання бази.

## Перевірка валідації

Усі кінцеві точки перевірено вручну через Swagger UI: 31 позитивна й негативна перевірка з очікуваними статус-кодами й кодами помилок. Прогін 2026-10-08: усі 31 збіглися з очікуваним. Результати — у [validation-checks.md](validation-checks.md).

## Знайдені розбіжності

1. **`405` відсутній у специфікації, хоча працює.** Підтверджено прогоном: `PUT /organizations` повертає `405` з кодом `METHOD_NOT_ALLOWED`, але в згенерованому `/v3/api-docs` жодна операція не оголошує `405`, а в `components/responses` є лише `BadRequest`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`.
2. **`500 INTERNAL_ERROR` описаний у `api-design.md`, але не оголошений у специфікації.** Спільної відповіді `InternalError` у згенерованому документі немає. Варто додати її, або прибрати код із таблиці помилок.
3. **`401` і `403` задокументовані, але недосяжні.** JWT у заглушках не перевіряється, тож через Swagger UI їх не перевірити. Ціль безпеки тому вимірює **контракт** (чи оголошено), а не поведінку; поведінку перевіримо після реалізації Auth Module.
4. **Некодована кирилиця в параметрі `q` ламає каркас помилок.** `GET /organizations?q=клуб` із сирими UTF-8 байтами відхиляється Tomcat і повертає `400` **у вигляді HTML-сторінки**, без `code` і `requestId`. З URL-кодуванням — `200`. Браузери кодують самі, тож у Swagger UI це не видно, але інший клієнт отримає відповідь у форматі, якого немає в контракті.
5. **PATCH з порожнім тілом повертає `200`** без змін (V-24). Поведінка перевірена й зафіксована, але в `api-design.md` не описана.
6. **Ліміт частоти запитів не реалізовано.** Для цілі продуктивності це означає, що єдиний захист від навантаження — пул з'єднань.
7. **`contactEmail` повертається публічно.** Це контакт організації, а не особи, тож NFR-009 не порушено. Але коли з'явиться дошка оголошень із контактами людей, знадобиться окремий рядок перевірки на витік.
8. **Вимірювання продуктивності на заглушках не репрезентативне:** дані лежать у `ConcurrentHashMap`, цифри будуть оптимістичні.
