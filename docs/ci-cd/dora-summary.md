## Що вважається розгортанням

**Розгортання** означає зелений запуск workflow CI (`.github/workflows/ci.yml`, jobs `Build and Test Backend` і `Build and Test Frontend`) на `main`.

Lint, SonarQube Cloud, API Docs, Deploy API Docs і ручний Build and Deploy не враховано; причини наведено в [`metrics-raw.md`](metrics-raw.md).

DORA визначає розгортання як викладку в робоче середовище, а ми рахуємо зелений CI. Тому всі результати нижче є **наближенням**.

Застосунок уже працює на сервері — https://b2b-saas-naukma.duckdns.org/ (образи збирає ручний Build and Deploy, у кластер їх викочує ArgoCD із гілки `deploy`). Сервер з'явився після вікна Етапу 1, тож для зіставності метрики лабораторної й далі рахуються за зеленим CI. Варіант «розгортання = публікація образу» — у бонусі 5.

- **Швидкість:** близько 6 розгортань на тиждень і медіана виконання змін менше доби. Це краще за більшість опитаних DORA (24–45%). Вузьке місце не в CI, а в довгому житті PR: #69 і #70 чекали злиття 5–6 діб.

## Бонуси

### Бонус 1. Автоматичний підрахунок метрик

Скрипт [`scripts/dora_metrics.py`](../../scripts/dora_metrics.py) через `gh api` (GitHub REST) бере запуски workflow CI на `main`, jobs кожного запуску, коміти `main` і злиті PR з їхніми комітами. Він рахує чотири метрики за визначеннями цієї лабораторної, чергу й виконання окремо. Результат для вікна Етапу 1 — [`dora-auto.md`](dora-auto.md).

```bash
gh auth login                                                     # один раз
python3 scripts/dora_metrics.py --output docs/ci-cd/dora-auto.md  # вікно Етапу 1
python3 scripts/dora_metrics.py --since 2026-11-13T00:00:00Z --until 2026-11-20T00:00:00Z  # інше вікно, у stdout
python3 -m unittest scripts/test_dora_metrics.py                  # тести розрахунків, без мережі
```

Скрипт лише читає API і запускається локально, без розкладу. «Запуск містить зміни PR» визначено так: історія `main` лінійна (squash), тож запуск містить merge-коміт PR, якщо його head не старіший. Зміни доставляє перший такий зелений запуск — так само, як вручну для #77, #79 і #102.

### Бонус 2. Покращення з виміряним ефектом: один job статичного аналізу замість трьох

**Проблема.** На кожен пуш у `main` (і на кожен PR) ішли три jobs статичного аналізу на спільних self-hosted раннерах курсу: `Lint Backend`, `Lint Frontend` (`lint.yml`) і `SonarQube Cloud Analysis` (`sonar.yml`). Sonar уже робив checkout, ставив JDK і Node, виконував `npm ci` і компілював та тестував бекенд. Lint повторював усю цю підготовку ще двічі тільки для того, щоб запустити Checkstyle, SpotBugs, ESLint, Prettier і `npm audit`. Черга на раннери — єдиний помітний внесок CI в час виконання змін (178 хв 01.11, див. розділ 3), тому кожен зайвий job на коміт — це місце в черзі, яке забирають і в нас, і в інших команд.

**Дія.** Лінтери перенесено в job Sonar (`.github/workflows/sonar.yml`, тепер workflow **Static Analysis**), `lint.yml` видалено:
- бекенд: `./mvnw verify sonar:sonar` замість `./mvnw test sonar:sonar -Dcheckstyle.skip`. Checkstyle (фаза `validate`) і SpotBugs (`verify`) працюють у тому самому запуску Maven, що й тести та аналіз, без окремої компіляції;
- фронтенд: ESLint, Prettier і `npm audit` використовують `node_modules`, який Sonar і так встановлює;
- лінтери, як і раніше, лише звітують (`failOnViolation=false`, `continue-on-error`), підсумок і звіти — у тому ж job. Обов'язкові перевірки (`Build and Test Backend/Frontend`) не змінено.

### Бонус 3. Швидкий і повільний набори тестів

| Набір | Що входить | Як запускається | Коли в CI |
|---|---|---|---|
| Швидкий | усе без `@Tag("integration")`: 271 тест бекенду | Surefire, `./mvnw test` | кожен PR і push у `main` (job `Build and Test Backend`) |
| Повільний | `@Tag("integration")`, 52 тести: 4 `*FlowIntegrationTest` (повний Spring-контекст + MockMvc) і 6 класів на PostgreSQL (`Jdbc*RepositoryTest`, `BoardConcurrencyPostgresTest`) | Failsafe, `./mvnw verify` | лише push у `main` (job `Integration Tests`) |

**Справжня залежність у контейнері.** Тести на PostgreSQL отримують базу з [`support/TestDatabase`](../../src/test/java/ua/edu/ukma/community/support/TestDatabase.java). Testcontainers через Docker раннера піднімає `postgres:17` (той самий мажор, що CloudNativePG у кластері), накочує міграції з `infra/migrations` і віддає JDBC URL. Контейнер один на прогін, після JVM його прибирає Ryuk.

Раніше тут був `embedded-postgres` без Docker, бо Docker на раннерах не був гарантований. Тепер його наявність підтверджує Build and Deploy (buildx) і окремий крок `docker info` у job.

Налаштування:
- Surefire `excludedGroups=integration`, Failsafe `groups=integration` ([`pom.xml`](../../pom.xml));
- job `Integration Tests` у [`ci.yml`](../../.github/workflows/ci.yml) з умовою `github.event_name == 'push'`;
- Static Analysis запускає лише швидкий набір (`-DskipITs`);
- Testcontainers піднято до 1.21.4: версія 1.21.3 зі Spring Boot 3.5.6 не працює з Docker Engine 29+.

**Компроміс.** Покриття рядків лише швидким набором — 63,9% проти 86,7% з усіма тестами. Поріг `jacoco-check` (50%) виконано, але Sonar бачить менше покриття нового коду, бо інтеграційні тести тепер ідуть тільки на `main`.

**Тривалість наборів:** _посилання на PR-запуск (лише швидкий набір) і на `main`-запуск (обидва) — після злиття._

### Бонус 4. Пошук нестабільних тестів

Workflow [`Flaky Test Hunt`](../../.github/workflows/flaky-tests.yml) запускається лише вручну (`workflow_dispatch`) і займає один раннер, без матриці. В одному job він раз компілює бекенд, а потім циклом N разів (за замовчуванням 5, менше не дозволено) проганяє повний набір тестів на тому самому коміті: `surefire:test` бекенду і Vitest фронтенду. JUnit-звіти кожного повтору зберігаються окремо. Повторів усередині Surefire немає, щоб не сховати нестабільність.

Скрипт [`scripts/flaky_tests.py`](../../scripts/flaky_tests.py) порівнює повтори. Тест, що в одних повторах пройшов, а в інших упав, — нестабільний, і тоді запуск червоний. Тест, що падав щоразу, виводиться окремо як зламаний. Таблиця — у Summary запуску, звіти — в артефакті `flaky-test-reports`.

Перевірено локально: один повтор циклу workflow (299 тестів бекенду, 77 фронтенду) і аналіз п'яти повторів — 376 тестів, нестабільних 0. З навмисно зіпсованим звітом в одному повторі тест знайдено, код виходу 1. Тести самого скрипта: `python3 -m unittest scripts/test_flaky_tests.py`.

**Повторні запуски на `main` за вікно Етапу 1**, що стали зеленими без зміни коду (`run_attempt` > 1): немає. Кожен із 20 запусків CI має одну спробу ([`dora-auto.md`](dora-auto.md), розділ «Повторні запуски»).

**Запуск workflow:** _посилання й результат — після злиття: `workflow_dispatch` доступний лише для workflow з гілки за замовчуванням._

### Бонус 5. Образ застосунку з кожного зеленого запуску на `main`

**Як працює.** Workflow [`Publish Images`](../../.github/workflows/publish-images.yml) запускається через `workflow_run`, коли завершився CI на `main`. Job виконується, лише якщо той запуск зелений і викликаний push'ем, тобто не скасований і не з PR.
- Збирає образи backend, frontend і migrations: multi-arch, як у Build and Deploy, зі спільним кешем.
- Пушить їх у GHCR з тегом, що дорівнює SHA перевіреного коміту. Checkout і тег беруться з `github.event.workflow_run.head_sha`: у `workflow_run` змінна `github.sha` — це останній коміт `main`, а не той, що перевірив CI.
- Логін — `GITHUB_TOKEN` з `packages: write`.
- Один job без матриці, тобто один раннер. `concurrency` без скасування, щоб не обірвати напівзапушений набір образів.

**Чому окремо від деплою.** Build and Deploy лишається ручним і вирішує, *що* їде на сервер, а цей workflow лише публікує образи. Саме тут 01.11 і був збій процесу: ручний деплой `ba81c05` завершився о 01:35, а зелений CI того самого коміту — о 02:35 ([`metrics-raw.md`](metrics-raw.md#ручний-деплой-того-ж-вечора)). З новим workflow образ не з'являється без зеленого CI.

**Метрики, якщо розгортання — публікація образу.** У вікні Етапу 1 (22.10–12.11) образи публікував лише ручний Build and Deploy, на `main` — один раз. Підрахунок — скриптом бонусу 1, якому для цього додано параметр `--event`:

```bash
python3 scripts/dora_metrics.py --workflow build-and-deploy.yml --event workflow_dispatch   # вікно Етапу 1
python3 scripts/dora_metrics.py --workflow publish-images.yml --event workflow_run --since <злиття> --until <дата>
```

| Метрика | Розгортання = зелений CI | Публікація образу вручну (вікно Етапу 1) | Публікація образу автоматично (після злиття) |
|---|---|---|---|
| Частота розгортань | 17 / 2,97 = **5,7 на тиждень** | 1 / 2,97 = **0,3 на тиждень** | _після злиття_ |
| Час виконання змін | медіана **20,5 год**, середнє 35,4 (n = 20) | медіана **94,8 год**, середнє 121,1 (n = 13; ще 11 PR за вікно образу так і не отримали) | _після злиття_ |
| Частота збоїв змін | 0% | 0% (0 з 1) | _після злиття_ |
| Час відновлення | немає даних | немає даних | _після злиття_ |
| Тривалість запуску | медіана виконання 2,0 хв, із чергою 2,5 хв | 7,6 хв виконання, 105,2 хв черги (01.11) | _після злиття_ |

**Висновок.** Якщо розгортанням вважати публікацію образу, ми розгортались у 17 разів рідше, а зміни чекали на образ у 4,6 раза довше. Єдина публікація стояла в черзі 105 хв і завершилась на годину раніше за зелений CI. Автоматична публікація після кожного зеленого CI має зрівняти перші два стовпці.

**Докази:** _посилання на запуск `Publish Images` і на сторінку пакета — після злиття: `workflow_run` спрацьовує лише з файлу на гілці за замовчуванням._
