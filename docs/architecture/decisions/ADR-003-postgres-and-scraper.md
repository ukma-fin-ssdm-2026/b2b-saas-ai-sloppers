# ADR-003: PostgreSQL і Scraper Worker

- **Статус:** future
- **Дата:** 2026-09-30
- **Учасники рішення:** Architecture (Artem Butyrin)
- **Пов’язано:** [ADR-001](ADR-001-architectural-style.md), NFR-001…007, NFR-013

## Context

Сервісу потрібні:
- надійне збереження організацій, подій, оголошень, ролей, статусів скрейпера;
- дедуплікація подій (NFR-005) і цілісність при паралельних запитах (NFR-006);
- фоновий збір анонсів із соцмереж (FR Scraper Worker) без зупинки API при помилці одного джерела (NFR-007);
- просте розгортання в Minikube.

## Decision

1. **Єдина БД сервісу — PostgreSQL** (одна схема / один логічний database для нашого мікросервісу в семестрі). Обмеження унікальності (UNIQUE) і транзакції БД — основний захист від дублікатів і гонок.
2. **Scraper Worker** — окремий запланований процес (cron / scheduled job) **у межах того самого сервісу**, який:
   - читає активні джерела;
   - тягне пости по HTTP;
   - пише чернетки подій у PostgreSQL (статус «На модерації» або автопублікація за налаштуванням);
   - ізолює збій одного джерела (retry), не валячи інші.
3. Окремий брокер повідомлень.

## Alternatives considered

| Альтернатива | Чому ні зараз |
|--------------|---------------|
| Scraper як окремий мікросервіс зі своєю БД | Ускладнює деплой і узгодженість даних для команди 4 / 10 тижнів; немає вимог масштабу Netflix. |
| Черга повідомлень між API і скрейпером | Корисна пізніше; зараз cron + БД достатні для обсягу ~20 джерел. |
| Інша СКБД (MongoDB тощо) | Слабша підтримка реляційної цілісності для ролей/місць/унікальних постів; стек курсу вже Java + SQL. |
| In-memory / H2 у проді | Не відповідає NFR надійності та репліки в Minikube. |

## Consequences

**Плюси**
- Проста операційна модель: API + Worker + PostgreSQL.
- NFR дедупу й цілісності закриваються механізмами БД.
- Легко показати на діаграмі компонентів і в деплої (один сервіс, один том БД).

**Мінуси / ризики**
- Worker і API ділять БД → сильніше зчеплення, ніж у «database per service» (прийнятно для семестру; межа мікросервісу - на рівні платформи SmartUkma).
- Довгий скрейп може конкурувати за з’єднання БД - обмежити пул і розклад cron.
- Точність NLP/regex скрейпера обмежена (NFR-013) -> обов’язкова модерація головою.
