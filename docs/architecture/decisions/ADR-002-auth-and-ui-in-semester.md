# ADR-002: AuthZ і UI у семестрі

- **Статус:** Under consideration
- **Дата:** 2026-09-30
- **Учасники рішення:** Architecture (Artem Butyrin)

## Context

За міні-ТЗ і [Project-Description](../../../Project-Description.md) цільова інтеграція:
- автентифікація / глобальні ролі -> SmartUkma `account-server`;
- рендер UI -> `ui-constructor`.

У семестрі потрібно все одно здати працюючу реєстрацію, ролі (Global Admin / Голова / User) і клієнтський інтерфейс. Делегування AuthZ/UI винесено **поза обсяг** семестру.

## Decision

1. **AuthZ у семестрі** - власний модуль у Community Events Service: реєстрація з `@ukma.edu.ua`, підтвердження email, логін, JWT, перевірка ролей (ABAC для голови організації).
2. **UI у семестрі** — окремий **React**-клієнт, який ходить у наш REST API.
3. **Після семестру** — Auth Module замінюється / проксується на `account-server`; UI може віддавати JSON для `ui-constructor` замість самостійного SPA (межа мікросервісу з ADR-001 зберігається).

## Alternatives considered

| Альтернатива | Чому ні зараз |
|--------------|---------------|
| Одразу інтегрувати `account-server` і `ui-constructor` | Немає гарантованого доступу/стабільного контракту в навчальному середовищі; блокує демо Lab. |
| Без UI  | Слабше покриття зручності та сценаріїв модерації/дошки; гірше для демо. |
| OAuth через зовнішнього провайдера | Явно поза обсягом міні-ТЗ. |

## Consequences

**Плюси**
- Повний вертикальний зріз фіч у семестрі (реєстрація -> каталог -> модерація -> дошка).
- Чітка точка заміни AuthZ/UI пізніше без переписування домену Orgs/Events/Board.

**Мінуси / ризики**
- Подвійна робота з безпекою.
- Ризик "протікання" логіки Auth у доменні модулі - тримати Auth окремим модулем.
