# Модель даних

Логічна ER-модель сервісу «Студентське ком'юніті та Івенти». Діаграма: [`uml/data-model.puml`](uml/data-model.puml). Фізична схема — міграції Flyway у [`infra/migrations/`](../../infra/migrations/) ([ADR-005](decisions/ADR-005-database-migrations.md)).

Цільова СУБД — PostgreSQL (локально — контейнер, віддалено — Supabase). Усі первинні ключі — `uuid`. Усі часові мітки — `timestamptz` і зберігаються в UTC; перетворення в Europe/Kyiv відбувається лише під час відображення та експорту в календар (NFR-011). Технічні таблиці (історія міграцій Flyway) у модель не входять. На всіх таблицях увімкнено Row Level Security, щоб закрити їх від REST API Supabase: доступ до даних — лише через бекенд.

На діаграмі заплановані сутності позначені стереотипом `<<план>>`, а заплановані поля реалізованих таблиць — коментарем `(план)`.

## Покриття ключових функцій

| Ключова функція | Сутності |
|---|---|
| Реєстрація та автентифікація | `app_user` |
| Керування головами організацій | `organization_head`, `role_change`, `app_user` |
| Каталог організацій | `organization`, `tag`, `organization_tag` |
| Збір подій скрейпером | `scraper_source`, `event` |
| Модерація та публікація подій | `event`, `organization` |

Додатково модель покриває модерацію користувачів і контенту (`ban`, `complaint`, `banned_word`) та рейтинги (`author_rating`, `organization_rating`).

## Сутності

### Користувачі та доступ

**app_user** — зареєстрований студент (назва `user` зарезервована в PostgreSQL). `email` зберігається в нижньому регістрі (`CHECK`), тож `UNIQUE` працює без урахування регістру. `status`: `PENDING` — пошту ще не підтверджено, вхід заборонено; `ACTIVE`; `BLOCKED`. `global_admin = true` — суперадмін; окрема таблиця ролей не потрібна, бо Global Admin не має власних атрибутів. Роль голови тут не зберігається, бо вона локальна для організації (див. `organization_head`). Поля `verification_code_hash`, `verification_expires_at`, `verification_attempts`, `verification_sent_at` зберігають поточний код підтвердження: одночасно в користувача активний лише один код, новий перезаписує старий (FR-002, FR-003).

**ban** *(план)* — блокування користувача на строк (FR-054). `banned_by = null` означає автоматичне блокування (FR-060), `expires_at = null` — безстрокове. Розблокування фіксується полями `lifted_by` і `lifted_at`, рядок не видаляється. Користувач вважається заблокованим, якщо існує бан з `lifted_at IS NULL` і `expires_at` порожнім або в майбутньому.

### Організації

**organization** — студентська організація. `slug` — унікальний ідентифікатор для URL у форматі `kebab-case` (`CHECK`). `instagram_handle` — публічний Instagram для профілю (FR-016); він не визначає, що парсить скрейпер (див. `scraper_source`). `logo_url` — посилання на логотип у Supabase Storage, сам файл у БД не зберігається. `auto_publish` вмикає автопублікацію спаршених подій, за замовчуванням `false` (FR-029). Заплановане поле `archived_at`: не порожнє — організація в архіві і разом із подіями не показується в каталогах (FR-015).

**tag**, **organization_tag** *(план)* — теги організацій зі зв'язком багато-до-багатьох (FR-014, FR-019). Теги винесено в окрему таблицю, щоб мати єдиний словник без дублікатів на кшталт «дебати» / «Дебати».

**organization_head** — активне призначення користувача головою конкретної організації (ABAC, FR-006). Первинний ключ `(organization_id, user_id)`: людина не може бути головою однієї організації двічі. Зняття ролі видаляє рядок, а історія зберігається в `role_change`. Призначення Global Admin самого себе головою відбувається так само.

**role_change** — журнал змін ролей голів (FR-013): хто (`actor_user_id`), кому (`target_user_id`), у якій організації, що (`APPOINTED` / `REMOVED`) і коли. Рядки тільки додаються. `actor_user_id = null`, якщо акаунт того, хто змінив роль, згодом видалено.

### Джерела та події

**scraper_source** *(план)* — Instagram-акаунт, підключений головою для скрейпера (FR-021, FR-022). Сутність існує виключно для Scraper Worker: `enabled` дозволяє тимчасово вимкнути збір, а `last_run_at`, `last_run_status`, `last_error` показують голові результат останнього запуску (FR-028, NFR-007). Єдиний тип джерела — `INSTAGRAM` (FR-067); поле `type` залишено як точку розширення. `scraper_source.url` може збігатися з `organization.instagram_handle`, але це різні дані: перше визначає, що парсити, друге — що показувати в профілі. Токени доступу до соцмереж у БД не зберігаються (NFR-010).

**event** — подія організації, створена скрейпером або головою вручну (FR-037). Заповнений `source_id` означає, що подію створив скрейпер; для ручних подій `source_id = null`. Поки таблиці `scraper_source` немає, `source_id` — просто `uuid` без зовнішнього ключа; FK з `ON DELETE SET NULL` додасть міграція скрейпера. `external_post_id` — ідентифікатор поста в Instagram, `original_url` — посилання на оригінал (FR-027). `image_url` — постер у Supabase Storage. Видалення організації каскадно видаляє її події.

Статуси: `PENDING` (на модерації, невидима Гостям і User; FR-030), `PUBLISHED`, `REJECTED` (відхилена головою; FR-035), `UNPUBLISHED` (знята з публікації після публікації; FR-036). `verified = false` позначає автоопубліковану подію, яку голова ще не переглянув (FR-032).

У дайджест потрапляють події зі статусом `PUBLISHED` і `starts_at` у майбутньому (FR-038); після появи `archived_at` — ще й з організацією не в архіві. Для цього запиту є індекс `(status, starts_at)`.

### Дошка оголошень *(план)*

**advert** — оголошення про пошук команди (`TEAM`) чи компанії для дозвілля (`LEISURE`) (FR-043). `contact` обов'язковий (FR-044) і є персональними даними (див. нижче). `status`: `ACTIVE`, `CLOSED` (закрите вручну, за дедлайном або після заповнення `slots`; FR-050, FR-051), `DELETED`. Оголошення заблокованого автора приховуються за наявністю активного бану, окремого статусу для цього немає (FR-055).

**advert_response** — відгук на оголошення (FR-046). `status`: `PENDING`, `CONFIRMED` (автор підтвердив, відгукувач бачить контакт; FR-049), `REJECTED`, `WITHDRAWN` (відкликаний до підтвердження; FR-053).

### Модерація контенту *(план)*

**complaint** — скарга на оголошення або відгук (FR-056). Замість поліморфного `target_id` використано два nullable зовнішні ключі `advert_id` і `response_id`, щоб цілісність гарантувала БД. `status`: `OPEN`, `RESOLVED` (контент видалено; FR-057), `DISMISSED`.

**banned_word** — список заборонених слів для автофільтра, веде Global Admin (FR-058).

### Рейтинги *(план, пріоритет Низький)*

**author_rating** — оцінка автора учасником закритого оголошення (FR-061). Середній рейтинг обчислюється запитом (FR-062).

**organization_rating** — оцінка організації користувачем, яку можна змінити (FR-063). Рейтинги зберігаються окремими записами, а не агрегованим полем, бо потрібно знати, хто вже оцінив (обмеження «один раз») і яку оцінку змінити.

## Обмеження цілісності

Реалізовані (у міграціях):

| Обмеження | Сутність | Вимога |
|---|---|---|
| `UNIQUE(email)` + `CHECK(email = lower(email))` | `app_user` | FR-001 |
| `CHECK(status IN ('PENDING','ACTIVE','BLOCKED'))` | `app_user` | FR-002, FR-004 |
| `UNIQUE(slug)` + `CHECK` формату `kebab-case` | `organization` | FR-014 |
| `PRIMARY KEY(organization_id, user_id)` — одне активне призначення на пару | `organization_head` | FR-008 – FR-010 |
| `CHECK(action IN ('APPOINTED','REMOVED'))` | `role_change` | FR-013 |
| `UNIQUE(source_id, external_post_id)` — повторний або паралельний запуск скрейпера не створює дублікатів | `event` | FR-025, NFR-005 |
| `CHECK(status IN ('PENDING','PUBLISHED','UNPUBLISHED','REJECTED'))` | `event` | FR-030 – FR-036 |
| `ON DELETE CASCADE` від `organization` | `event`, `organization_head`, `role_change` | FR-015 |

Заплановані (разом із відповідними таблицями):

| Обмеження | Сутність | Вимога |
|---|---|---|
| FK `event.source_id` → `scraper_source` з `ON DELETE SET NULL` — видалення джерела не видаляє події | `event` | FR-022 |
| `UNIQUE(advert_id, user_id)` — один відгук на оголошення | `advert_response` | FR-046 |
| `CHECK` — заповнено рівно одне з `advert_id`, `response_id` | `complaint` | FR-056 |
| `UNIQUE(rater_id, advert_id)` | `author_rating` | FR-061 |
| `UNIQUE(user_id, organization_id)` | `organization_rating` | FR-063 |
| `CHECK(score BETWEEN 1 AND 5)` | `author_rating`, `organization_rating` | FR-061, FR-063 |
| `CHECK(slots > 0)` | `advert` | FR-043 |

Інваріанти, які схемою не виражаються і забезпечуються транзакціями з блокуванням рядків (NFR-006):

- в організації завжди є щонайменше один голова (FR-011, FR-014);
- кількість відгуків зі статусом `CONFIRMED` не перевищує `advert.slots`; досягнення ліміту закриває оголошення (FR-050).

Виявлення дублікатів однієї події з різних джерел (FR-026) ґрунтується на нечіткому збігу назви, тому виконується логікою Scraper Worker (`DedupKey`), а не обмеженням БД.

## Персональні та чутливі дані

| Поле | Категорія | Хто має доступ |
|---|---|---|
| `app_user.email` | PII | сам користувач, Global Admin; голова — під час призначення голови за email |
| `app_user.password_hash` | секрет (bcrypt) | лише сервіс автентифікації; не повертається в API і не пишеться в логи (NFR-008) |
| `app_user.verification_code_hash` | секрет | лише сервіс автентифікації |
| `organization.contact_email` | контакт організації | публічний, показується в профілі |
| `advert.contact` *(план)* | PII | автор і підтверджені відгукувачі; для решти не повертається в жодній відповіді, лозі чи помилці (FR-049, NFR-009) |
| `advert_response.message` *(план)* | PII (довільний текст) | автор відгуку, автор оголошення, Global Admin при розгляді скарги |
| `ban.reason` *(план)* | чутливе | Global Admin, заблокований користувач |
| `role_change` (історія) | внутрішнє | голови цієї організації, Global Admin (FR-013) |
