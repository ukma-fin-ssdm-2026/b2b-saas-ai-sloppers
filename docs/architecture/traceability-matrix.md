## 4. Знайдені розбіжності

1. **Модерація користувачів (FR-054 – FR-060) не має власного компонента.** Блокування людини, розгляд скарг, список заборонених слів і ліміти частоти зараз «розмазані» між Auth Module і Bulletin Board. Це різні за природою обов'язки: Auth відповідає за особу, Board — за контент, а модерація платформи — за поведінку. Варіанти: або виділити окремий Moderation Module, або явно записати в HLD, який модуль що з цього несе.
2. **NFR-004 (відмовостійкість БД) не перевіряється на рівні компонентів.** У діаграмі компонентів PostgreSQL — один блок, а вимога говорить про репліку й відновлення ≤ 30 с. Це рівень розгортання, тож діаграма розгортання (issue #35) має показати два поди БД, інакше вимога лишиться без візуального підтвердження.
3. **React Web Client не має жодної власної вимоги.** Усі 68 FR сформульовані як «Система повинна…» і описують бекенд. Клієнт при цьому в обсязі семестру. Якщо не додати бодай кількох вимог до UI, компонент лишиться в архітектурі без замовлення.
4. **ui-constructor (F-02) не покритий жодною вимогою.** На відміну від account-server, який спирається на FR-066, для нього такої вимоги немає. Або додати рядок у розділ Won't, або прибрати з діаграми як припущення.
5. **Успадковано з Лабораторної 2:** FR-021 суперечить FR-067 (Instagram або WhatsApp проти «лише Instagram»), а FR-016 має пріоритет Must без жодної історії. Це впливає на архітектуру: у компоненті C-07 тип джерела спроєктовано як enum з двома значеннями, і якщо WhatsApp таки поза обсягом, друге значення зайве. Issues [#22](../../issues/22), [#23](../../issues/23).

## 5. Сценарії атрибутів якості

Сценарії записано в шестичастинному форматі: джерело — стимул — артефакт — середовище — відповідь — міра відповіді.

### QS-01 · Продуктивність (NFR-001, NFR-002)

| Частина            | Значення                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Джерело**        | Студенти, які відкривають каталог подій                                                                     |
| **Стимул**         | 100 одночасних користувачів надсилають GET-запити до каталогу подій і організацій                           |
| **Артефакт**       | C-02 API Controllers, C-05 Events & Moderation, C-09 PostgreSQL                                             |
| **Середовище**     | Штатна робота, піковий день (анонс великої події), Scraper Worker одночасно виконує запланований цикл збору |
| **Відповідь**      | Сервіс обробляє запити на читання; фоновий збір не блокує обробку HTTP-запитів                              |
| **Міра відповіді** | p95 ≤ 500 мс при 50 паралельних користувачах; частка 5xx < 1% при 100 користувачах протягом 5 хвилин        |

**Архітектурне рішення, яке це забезпечує:** винесення скрейпінгу у фоновий воркер (ADR-001). Звернення до Instagram триває секунди, тож у синхронному шляху запиту воно зробило б цільові 500 мс недосяжними.

**Верифікація:** TC-043, TC-044 — навантажувальний тест k6 на читальних ендпоінтах із паралельним запуском воркера.

### QS-02 · Безпека та приватність (NFR-009)

| Частина            | Значення                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Джерело**        | Автентифікований користувач, який не є ні автором оголошення, ні підтвердженим відгукувачем                                          |
| **Стимул**         | Запит списку оголошень, сторінки оголошення та списку відгуків                                                                       |
| **Артефакт**       | C-06 Bulletin Board, C-02 API Controllers                                                                                            |
| **Середовище**     | Штатна робота; оголошення активне, відгук користувача ще не підтверджено або вже відхилено                                           |
| **Відповідь**      | Система повертає дані оголошення без поля контакту; контакт не з'являється ні у відповіді, ні в повідомленні про помилку, ні в логах |
| **Міра відповіді** | 0 випадків витоку контакту на всіх ендпоінтах оголошень і відгуків у автоматизованому тесті                                          |

**Архітектурне рішення:** дві окремі проєкції оголошення замість однієї сутності з умовним заповненням поля. Умовне заповнення рано чи пізно повертає контакт через якийсь із ендпоінтів; окремий публічний DTO робить витік неможливим за побудовою.

**Верифікація:** TC-030, TC-033, TC-036 — автотест, який перебирає всі ендпоінти дошки від імені трьох ролей (автор, підтверджений, сторонній) і шукає поле контакту у відповідях і логах.

### QS-03 · Надійність (NFR-005, NFR-007)

| Частина            | Значення                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **Джерело**        | Scraper Worker за розкладом cron                                                                                           |
| **Стимул**         | Цикл збору, під час якого одне з джерел недоступне, а той самий анонс опубліковано у двох джерелах організації             |
| **Артефакт**       | C-07 Scraper Worker, C-09 PostgreSQL, E-01 Instagram / WhatsApp                                                            |
| **Середовище**     | Штатна робота; можливий паралельний запуск двох циклів збору                                                               |
| **Відповідь**      | Недоступне джерело не перериває обробку решти (до 3 повторних спроб, статус помилки збережено); подія створюється один раз |
| **Міра відповіді** | 0 дублікатів при паралельному запуску; 100% решти джерел опрацьовано попри помилку одного                                  |

**Архітектурне рішення:** дедуплікація покладена на UNIQUE-обмеження в базі, а не на перевірку в коді воркера. Перевірка «чи є така подія» в коді не рятує від стану гонки між двома запусками, обмеження в БД — рятує.

**Верифікація:** TC-021, TC-022, TC-045 — інтеграційні тести з підміненим джерелом і паралельним запуском воркера.
