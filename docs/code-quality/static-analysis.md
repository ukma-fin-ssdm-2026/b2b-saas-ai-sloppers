# Статичний аналіз

Звіт складається з двох частин: бекенд (Java, `src/`) і фронтенд (React / TypeScript, `web-src/`). Для кожної частини описано інструменти, покриття, знахідки й рішення щодо них.

Цифри в розділах «Результати» — з прогону на `main` **31.10.2026**, уже з модулями `auth` і `storage`. Прогін повторюється командами з розділів «Запуск»; у попередній редакції звіту були цифри від 14.10.2026, коли в проєкті ще не було ні бази даних, ні автентифікації.

## Backend (Java, `src/`)

### 1. Інструменти та конфігурація

| Інструмент                      | Версія  | Що перевіряє                       | Конфігурація                                 |
| ------------------------------- | ------- | ---------------------------------- | -------------------------------------------- |
| Checkstyle                      | 10.20.1 | стиль і стандарт кодування         | `config/quality/checkstyle.xml`              |
| SpotBugs                        | 4.8.6   | вади коректності й підтримуваності | налаштування в `pom.xml`                     |
| find-sec-bugs (плагін SpotBugs) | 1.13.0  | **вади безпеки**                   | налаштування в `pom.xml`                     |

Самого лінтера недостатньо, тому аналізатором безпеки виступає **SpotBugs із набором правил find-sec-bugs**: він знає специфічні для Java й Spring категорії (`SECURITY`, ін'єкції, криптографія, небезпечна десеріалізація).

**Стандарт кодування**
власний набір правил Checkstyle, базові величини як у конвенціях Spring Framework (відступ 4 пробіли, довжина рядка 120). Повний перелік правил із поясненнями — у коментарях `config/quality/checkstyle.xml`.

**Налаштування суворості:** `effort=Max`, `threshold=Low` — свідомо найчутливіший режим. Коли інструменти підключали, у проєкті було 16 класів і шум був керований. Зараз файлів 85, і найчутливіший режим дає 71 знахідку, з яких 69 — чотири групи підтверджених хибних спрацьовувань (розділ «Придушені правила»). Режим залишили: описати групу винятків один раз дешевше, ніж підняти поріг і проґавити знахідку в категорії, яку ми ще не бачили.

**Режим роботи — звітний.** Обидві перевірки виводять знахідки, але не валять збірку (`failOnViolation=false`, `failOnError=false`). Коли інструменти підключали, у коді було 20 стильових зауважень і блокуюча перевірка зупинила б роботу над CRUD. Зараз їх 129: код виріс швидше, ніж до нього дійшла стильова чистка. Перемикання в блокуючий режим досі відкрите, але воно вже не зводиться до «прибрати два рядки» — спершу треба ухвалити два рішення щодо самих правил (розділ «Результати»). Проміжний стан зафіксовано коментарями в `pom.xml`, щоб його не забули зняти.

**У CI** обидві перевірки запускає job `Lint Backend` у `.github/workflows/lint.yml` на кожен push і PR у `main`. Кількість знахідок (Checkstyle, SpotBugs, з них `SECURITY`) видно в Summary запуску, повні XML-звіти — в артефакті `backend-lint-reports`. У `ci.yml` лінтери вимкнені (`-Dcheckstyle.skip -Dspotbugs.skip`), щоб не запускатися двічі. Блокування вмикається тим самим прибиранням `failOnViolation`/`failOnError` у `pom.xml`, YAML змінювати не треба.

#### Запуск

```bash
./mvnw checkstyle:check          # стиль
./mvnw spotbugs:check            # безпека й коректність
./mvnw verify                    # обидва в межах збірки
```

Checkstyle підключений до фази `validate`, SpotBugs — до `verify`.

### 2. Покриття

Аналізом охоплено весь код проєкту: 85 файлів у `src/main/java` і 18 у `src/test/java` (`includeTests=true` в обох інструментах, `includeTestSourceDirectory=true` у Checkstyle). Згенерованого коду немає, зон поза аналізом немає.

Прогін `./mvnw clean verify` на `main` (31.10.2026, JDK 21): **129** зауважень Checkstyle і **71** знахідка SpotBugs, з яких **2** лишаються після чотирьох груп задокументованих винятків.

У `src/main/java` 87 зауважень, у `src/test/java` — 42. Усі 129 стосуються оформлення; дефектів поведінки Checkstyle не знайшов. `JavadocType`, якого в попередньому прогоні було 21, зник: Javadoc публічних типів написали разом із модулем `auth`.

**Головне не кількість, а те, що 94 зауваження зі 129 — це два рішення, а не 94 дефекти.**

`EmptyLineSeparator` — 64 зауваження, з них 63 у `src/main` і 59 на об'явах типів (`CLASS_DEF`, `RECORD_DEF`, `INTERFACE_DEF`, `ENUM_DEF`). Це одна послідовна звичка команди: два порожні рядки між імпортами й об'явою типу. Правило налаштоване як `allowMultipleEmptyLines=false`, тобто забороняє саме це. Варіанти: переформатувати весь код під правило або дозволити `allowMultipleEmptyLines` перед об'явою типу. Другий варіант чесніший — звичка однакова в усіх 63 місцях, тож це не недбалість, а наша конвенція, яку правило не враховує.

`MagicNumber` — 44 зауваження, з них **35 у тестах**: `offset=10`, `limit=20`, `3` очікуваних елементи в списку, `61` хвилина для перевірки простроченого коду підтвердження. У тестах числовий літерал на місці — він і є тестові дані, виносити його в константу означає ховати вхід сценарію. Причина шуму — `includeTestSourceDirectory=true`. Правильна правка не в коді, а в конфігурації: виключити `MagicNumber` для тестових джерел. Дев'ять зауважень у `src/main` залишаються змістовними — п'ять із них у `CalendarExportService` на межах діапазонів UTF-8 (`0x80`, `0x800`, `0x10000`), і там іменовані константи справді читалися б краще.

Решта 21 зауваження — звичайна чистка: `NewlineAtEndOfFile`, задовгі рядки, три `import ... .*`, два `if` без дужок.

**Виняток:** `ConstantName` для `log`. Ім'я `log` для логера — усталена практика в екосистемі Spring, і перейменування на `LOG` зробило б код менш звичним. Рішення за командою; поки залишено як зауваження.

**`NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE`** у `GlobalExceptionHandler.handleTypeMismatch:74`: аналізатор вважає можливим розіменування результату `ex.getRequiredType()`. У коді перевірка на `null` є (`ex.getRequiredType() == null ? "інший тип" : ...`), тож це хибне спрацювання тернарного оператора. Залишено без придушення: правило корисне, а один шумний випадок не привід його вимикати.

**`SE_BAD_FIELD`** в `ApiException`: несеріалізовне поле `details` у серіалізовному класі. Винятки в нас ніколи не серіалізуються, тож ризику немає.

**`CRLF_INJECTION_LOGS`** — єдина знахідка з категорії SECURITY, яка справді щось означала. Правило спрацьовує, коли в повідомлення лога підставляється значення ззовні: символ переносу рядка в ньому дозволяє дописати в журнал фальшивий рядок і замаскувати власні дії (CWE-117). Шість спрацьовувань: адреса пошти в `LogCodeSender` і `MailCodeSender`, шлях і повідомлення винятку в `SupabaseImageStorage`.

Виправлено в коді класом [`common/LogSafe`](../../src/main/java/ua/edu/ukma/community/common/LogSafe.java) (тести — `LogSafeTest`): він замінює переноси рядка на `_` перед записом, і застосований у всіх шести місцях. Знахідки при цьому **не зникли**, і це не недоробка: find-sec-bugs знає лише свій перелік санітайзерів і власний `LogSafe.of` за такий не вважає. Тобто це хибне спрацювання вже *після* виправлення, тому воно в фільтрі винятків.

#### Придушені правила

Чотири групи у [`config/quality/spotbugs-exclude.xml`](../../config/quality/spotbugs-exclude.xml); разом вони ховають **69 знахідок зі 71**. Кожна група має в файлі коментар із причиною.

| Група                                                                                    | Ховає | Причина                                                                                                              |
| ---------------------------------------------------------------------------------------- | ----- | -------------------------------------------------------------------------------------------------------------------- |
| `EI_EXPOSE_REP`, `EI_EXPOSE_REP2`                                                        | 25    | SpotBugs вважає змінним станом будь-який об'єкт у конструкторі; у Spring це інжектовані біни, спільні за задумом      |
| `SPRING_ENDPOINT`                                                                        | 28    | інформаційна позначка «перегляньте точку входу вручну», а не вразливість                                              |
| `BC_UNCONFIRMED_CAST`, `RV_RETURN_VALUE_IGNORED_*`, `NP_NULL_*` — лише в класах `*Test`   | 9     | тести навмисно передають `null` і відкидають результат, щоб перевірити, що виняток кидається                           |
| `CRLF_INJECTION_LOGS` у трьох класах                                                     | 6     | **уже не потрібна:** знахідки виправлено через `LogSafe`                                                              |

**Чому це компроміс, а не рішення.** Придушити 69 зі 71 знахідки — багато, і виглядає як спроба зробити звіт зеленим. Захист тут один: усі чотири групи звужені до конкретного правила або класу, а не вимикають категорію. Але дві з них варто переглянути:

- `SPRING_ENDPOINT` ховає рівно те правило, яке в розділі 4 привело нас до справжньої вразливості. Поки воно придушене, наступна незахищена точка входу не з'явиться у звіті. Корисніше залишити його видимим і раз на спринт переглядати список — саме для цього правило й зроблене.
- Виняток `CRLF_INJECTION_LOGS` виписаний на три класи цілком, а не на конкретні виклики. Поки що він ховає шість перевірених хибних спрацьовувань, але завтра хтось допише в `SupabaseImageStorage` лог без `LogSafe` — і сьома знахідка, уже справжня, теж не потрапить у звіт. Виняток треба звузити до рівня методу або замінити на `@SuppressFBWarnings` над самими викликами, щоб він старів разом із кодом, а не покривав клас наперед.

Обидві правки — в «Відкритих діях».

### 4. Задокументована вразливість

**Кінцеві точки запису доступні без автентифікації** — знайдено 14.10.2026, **закрито 31.10.2026** (див. «Стан» у кінці розділу).

|                  |                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Що**           | `POST`, `PATCH`, `DELETE /api/v1/organizations` виконуються без токена                                                                           |
| **Чим знайдено** | find-sec-bugs, правило `SPRING_ENDPOINT` (категорія SECURITY), 5 входжень у `OrganizationController`                                             |
| **Підтверджено** | ручним запитом: `curl -X DELETE .../organizations/{id}` без заголовка `Authorization` повертає `204`                                             |
| **Загроза**      | **T-02** з [threat-model.md](../architecture/threat-model.md) — Elevation of privilege: будь-хто може створити, змінити або видалити організацію |
| **Оцінка**       | Висока за наслідками, але зараз недосяжна ззовні: сервіс не розгорнутий, працює лише локально на заглушках у пам'яті процесу                     |

`SPRING_ENDPOINT` — інформаційне правило: воно не стверджує, що є вразливість, а каже «цю точку входу треба перевірити вручну». Перевірка показала, що `@SecurityRequirement` у контролері **документує** `bearerAuth`, `401` і `403`, але жодного фільтра автентифікації в застосунку немає. Тобто специфікація обіцяє захист, якого в коді немає — найгірший варіант, бо клієнт і рев'юер бачать у Swagger UI замок і вважають, що все гаразд.

**Рішення на той момент: ризик свідомо прийнято**, з такими умовами:

1. Сервіс не розгортається в публічну мережу, доки немає Auth Module (ADR-002).
2. У `api-design.md` і `quality-attributes.md` зафіксовано, що `401`/`403` наразі перевіряються лише як **контракт**, а не як поведінка.

#### Стан: закрито

Auth Module реалізовано (PR #74), і розбіжність між специфікацією та кодом зникла — `401`/`403` тепер поведінка, а не лише контракт.

| | |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Чим закрито** | [`auth/SecurityConfig.java`](../../src/main/java/ua/edu/ukma/community/auth/SecurityConfig.java): `anyRequest().authenticated()` як типове правило, а `permitAll()` — лише для реєстрації, входу, читання каталогу (FR-007), Swagger UI і `/actuator/health`. Права на рівні ролей — в `OrgRolePolicy` |
| **Чим доведено** | [`AuthFlowIntegrationTest`](../../src/test/java/ua/edu/ukma/community/auth/AuthFlowIntegrationTest.java) — наскрізно через `MockMvc`: `POST /organizations` без токена дає `401` і `WWW-Authenticate: Bearer`; студент із токеном — `403`; адмін — `201`; голова редагує профіль, сторонній студент — `403`; видалити організацію може лише адмін |
| **Що лишилося** | `SPRING_ENDPOINT` як правило придушене, тому незахищену точку входу тепер ловить не аналізатор, а цей тест. Тест перевіряє `organizations` і `auth`, але не `events` і не завантаження картинок — там те саме треба перевірити окремо |

**Чому це не означає «безпека зроблена».** Закрилася одна конкретна знахідка однієї загрози (T-02). Тест фіксує правила доступу для організацій; для подій і картинок такого тесту немає, а `SPRING_ENDPOINT` більше не підкаже, якщо хтось додасть точку входу без правила в `SecurityConfig`. Типове правило `anyRequest().authenticated()` тут головний захист: нова точка входу закрита, доки її явно не відкрили. Саме тому воно, а не перелік `permitAll()`, має залишатися останнім рядком у конфігурації.

### 5. Виправлена знахідка з регресійним тестом

**`DM_CONVERT_CASE` — залежний від локалі `toLowerCase()`**

Місця: `ErrorCode.anchor()` і `OpenApiConfig.example()`.

Виклик `name().toLowerCase()` без параметра означає `toLowerCase(Locale.getDefault())`, а типова локаль береться з операційної системи, де запущена JVM. У турецькій локалі `I` переходить у `ı` без крапки, тож `INVALID_PARAMETER` дає якір `ınvalıd-parameter`, і посилання в полі `documentation` кожної помилки веде в нікуди. Ризик для нашого розгортання низький, але клас помилки стає небезпечним, щойно `toLowerCase` з'явиться у звірці ролей чи розширень файлів — тому виправлено одразу.

Явна `Locale.ROOT` в обох місцях — нейтральна локаль без національних правил, саме те, що потрібно для рядків, призначених машині (коди помилок, URL, ключі), а не людині.

Регресійний тест [`ErrorCodeAnchorTest`](../../src/test/java/ua/edu/ukma/community/common/error/ErrorCodeAnchorTest.java) підставляє турецьку локаль і перевіряє якорі. Прогін на коді **до** виправлення:

```
expected: <invalid-parameter> but was: <ınvalıd-parameter>
Tests run: 2, Failures: 1
```

Після виправлення обидва тести проходять. Перевірка «тест справді падає до фіксу» обов'язкова: тест, який ніколи не падав, не доводить нічого — можливо, він перевіряє не те.

**Тест було втрачено й відновлено 31.10.2026.** Під час звірки цього звіту з кодом з'ясувалося, що `ErrorCodeAnchorTest` зник у коміті `6e11a75` (#64) — його видалили разом із реорганізацією тестів, не зауваживши призначення. `Locale.ROOT` у коді лишився, тому нічого не впало й ніхто не помітив: виправлення пережило свою охорону. Тест повернуто на місце (`Locale.of("tr", "TR")` замість задепрекейченого конструктора) і перевірено заново — без `Locale.ROOT` він падає з тим самим `ınvalıd-parameter`, що й у жовтні.

Це найцікавіше, що дав цей перегляд. Регресійний тест цінний не в день, коли його написали, а через місяць, коли хтось правитиме `anchor()` і не знатиме про турецьку локаль. Тест, який можна тихо видалити без жодного червоного прогону, цієї роботи не виконує. Звідси практичний висновок для команди: видалення тесту має обґрунтовуватися в PR так само, як зміна коду, — тест без явної причини видалення і є регресія, просто відкладена.

### 6. Висновки

**Стан коду прийнятний, але звіт тримається на винятках.** Знахідок із високим рангом ризику аналізатори не дали: усі 129 зауважень Checkstyle стосуються оформлення, а з 71 знахідки SpotBugs шість виправлено в коді (`CRLF_INJECTION_LOGS`), дві прийнято з обґрунтуванням, решта придушена як підтверджені хибні спрацьовування. Головне число тут не «2 знахідки», а «69 придушених»: без фільтра винятків звіт нечитний, із фільтром — майже порожній, і обидві крайності однаково погано показують стан коду.

**Шум — це теж дефект, лише в конфігурації.** 94 зауваження Checkstyle зі 129 — наслідок двох налаштувань, а не 94 помилок у коді: `allowMultipleEmptyLines=false` проти звички команди писати два порожні рядки перед об'явою типу, і `MagicNumber` на тестових даних через `includeTestSourceDirectory=true`. Доки це не виправлено, перевірку не можна зробити блокуючою: вона завалить збірку на оформленні, а не на дефектах. Тому «стильова чистка» з попередньої редакції звіту так і не відбулася — виявилося, що правити треба не код.

**Вразливість, задокументована в Lab 5, закрита.** Розбіжність «специфікація обіцяє `401`/`403`, код їх не перевіряє» зникла разом із Auth Module: тепер це поведінка, підтверджена `AuthFlowIntegrationTest`. Разом з нею, однак, придушилося й правило `SPRING_ENDPOINT`, яке до цієї вразливості привело, — тож гарантію тепер дає типове правило `anyRequest().authenticated()` і тест, а не аналізатор.

**Аналізатори нарешті мають на чому працювати.** У попередній редакції висновок був такий: find-sec-bugs перевіряє передусім SQL-ін'єкції, криптографію й десеріалізацію, а в проєкті не було ні бази, ні автентифікації, тому більшість детекторів не спрацьовувала. Зараз є і PostgreSQL із JDBC, і JWT, і виклики до сторонніх сервісів — і прогін одразу дав шість справжніх знахідок CWE-117, яких очима під час рев'ю не побачиш. Передбачення підтвердилося.

**Відкриті дії.**

1. Виключити `MagicNumber` для тестових джерел і ухвалити рішення щодо `EmptyLineSeparator` — це знімає 94 зауваження зі 129 без жодної правки в коді.
2. Прибрати решту 35 зауважень (переноси в кінці файлів, задовгі рядки, зоряні імпорти, дужки в `if`) і рішення команди щодо `ConstantName` для `log`.
3. Після цього зняти `failOnViolation`/`failOnError` у `pom.xml` і зробити `Lint Backend` обов'язковою перевіркою для `main`.
4. Звузити виняток `CRLF_INJECTION_LOGS` до конкретних викликів, щоб новий несанітизований лог у тих самих класах не ховався автоматично.
5. Повернути `SPRING_ENDPOINT` у звіт або додати тест правил доступу для `events` і завантаження картинок — зараз ці точки входу не перевіряє ні аналізатор, ні тест.

## Frontend (React / TypeScript, `web-src/`)

### 1. Інструменти та конфігурація

| Інструмент                       | Версія (`package.json`) | Що перевіряє                                  | Конфігурація                    |
| -------------------------------- | ----------------------- | --------------------------------------------- | ------------------------------- |
| ESLint + typescript-eslint       | 10.12 / 8.71            | помилки й підозрілі конструкції в TS/React    | `web-src/eslint.config.js`      |
| eslint-plugin-security           | 4.2                     | **небезпечні патерни** в JavaScript-коді      | набір `recommended`             |
| Prettier + eslint-config-prettier | 3.9                    | форматування                                  | `web-src/.prettierrc`           |
| npm audit                        | npm 11.8.0              | **відомі вразливості** в залежностях          | `--omit=dev`                    |

ESLint підключає набори `recommended` для JavaScript, TypeScript, `react-hooks`, `react-refresh` і `security`. `eslint-config-prettier` вимикає стильові правила ESLint, які конфліктують із Prettier, тож за форматування відповідає лише Prettier.

**Аналізатор безпеки** складається з двох частин: `eslint-plugin-security` шукає небезпечні патерни у власному коді (`eval`, динамічні регулярні вирази, доступ до об'єкта за змінним ключем), а `npm audit` перевіряє сторонні пакети за базою відомих вразливостей.

`npm audit` запускається з `--omit=dev`: у збірку для браузера потрапляють лише production-залежності, а інструменти розробки (Vite, ESLint) у браузері користувача не виконуються.

**Режим роботи — звітний у CI.** Job `Lint Frontend` у `.github/workflows/lint.yml` на кожен push і PR у `main` запускає ESLint, Prettier і `npm audit`. Кожен крок має `continue-on-error: true`: падіння видно в статусі кроку й у Summary запуску, але job і PR залишаються зеленими. Щоб перевірки почали блокувати, досить прибрати `continue-on-error`. Перевірку типів (`tsc -b`) виконує job `Build Frontend` у `ci.yml` у складі `npm run build`, тому тут вона не дублюється.

#### Запуск

```bash
cd web-src
npm run lint            # ESLint + eslint-plugin-security
npm run format:check    # Prettier
npm run audit           # npm audit --omit=dev
```

### 2. Покриття

ESLint перевіряє всі файли `**/*.{ts,tsx}` у `web-src/`: 9 у `src/` (з них два тестових) і три конфігураційних у корені — `vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`. Поза аналізом лише `dist/`, `node_modules/` і `coverage/`. Prettier додатково ігнорує `package-lock.json`.

**`security/detect-object-injection`** на виразі `text[charIndex]`. Правило спрацьовує на будь-який доступ за змінним ключем, бо через `obj[key]` зловмисник може дістатися до `__proto__` чи `constructor`. Тут це хибне спрацювання: `text` — рядок, а `charIndex` — число зі стану компонента, яке користувач не контролює.

Знахідку все одно виправлено, а не придушено: `text.charAt(charIndex)` робить те саме і правилу не суперечить. Переписати один вираз дешевше, ніж додавати `eslint-disable`, яке потім доводиться обґрунтовувати на кожному рев'ю. Придушень у коді немає.

### 4. Зв'язок із моделлю загроз

Для фронтенду головна загроза — **T-04** з [threat-model.md](../architecture/threat-model.md): скрипт, що потрапив у текст події чи організації, виконується в браузері відвідувача (XSS). Пом'якшення з моделі загроз — «екранування при виводі».

Каталог організацій виводить дані з API лише як текст у JSX, який React екранує автоматично. `dangerouslySetInnerHTML` у коді не використовується. Тобто зараз екранування забезпечує сам React, і воно залишиться дієвим, доки ніхто не вставляє HTML напряму.

### 5. Висновки

**Стан фронтенду прийнятний для поточного етапу.** Єдину знахідку аналізатора безпеки виправлено, вразливих production-залежностей немає.

**Покриття загроз досі обмежене обсягом коду.** Бекенд уже має автентифікацію, але клієнт її не споживає: у `web-src/` немає ні форми входу, ні збереження токена — лише читання публічного каталогу. Тому більшості правил `eslint-plugin-security` як і раніше немає на чому спрацювати. Прогін варто повторити саме тоді, коли логін з'явиться в UI: зберігання JWT у браузері — це нова поверхня атаки (**T-01** з [threat-model.md](../architecture/threat-model.md), у частині «використовує викрадений JWT від імені голови»), якої зараз у коді просто немає.

**Відкриті дії:** зняти `continue-on-error` і зробити `Lint Frontend` обов'язковою перевіркою для `main` — на відміну від бекенду, тут усі три перевірки вже проходять, тож блокуючий режим можна вмикати одразу; за потреби виводити HTML з описів подій — лише через санітайзер.

> Workflows запускаються на власних раннерах (`runs-on: [self-hosted, linux]`) — у попередній редакції тут було зазначено, що GitHub Actions вимкнені через оплату; це вже не так. Локально ті самі перевірки виконуються командами з розділів «Запуск». SpotBugs 4.8 потребує JDK 21 (на JDK 25 падає з `Unsupported class file major version 69`).
