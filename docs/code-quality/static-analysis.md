# Статичний аналіз

## 1. Інструменти та конфігурація

| Інструмент                      | Версія  | Що перевіряє                       | Конфігурація                                 |
| ------------------------------- | ------- | ---------------------------------- | -------------------------------------------- |
| Checkstyle                      | 10.20.1 | стиль і стандарт кодування         | `config/quality/checkstyle.xml`              |
| SpotBugs                        | 4.8.6   | вади коректності й підтримуваності | налаштування в `pom.xml`                     |
| find-sec-bugs (плагін SpotBugs) | 1.13.0  | **вади безпеки**                   | фільтр `config/quality/spotbugs-exclude.xml` |

Самого лінтера недостатньо, тому аналізатором безпеки виступає **SpotBugs із набором правил find-sec-bugs**: він знає специфічні для Java й Spring категорії (`SECURITY`, ін'єкції, криптографія, небезпечна десеріалізація).

**Стандарт кодування**
власний набір правил Checkstyle, базові величини як у конвенціях Spring Framework (відступ 4 пробіли, довжина рядка 120). Повний перелік правил із поясненнями — у коментарях `config/quality/checkstyle.xml`.

**Налаштування суворості:** `effort=Max`, `threshold=Low` — свідомо найчутливіший режим. На проєкті з 16 класів шум керований, а пропустити щось важливе дорожче.

**Режим роботи — звітний, у два етапи.** Зараз обидві перевірки виводять знахідки, але не валять збірку (`failOnViolation=false`, `failOnError=false`). Причина: на момент підключення в коді вже було 20 стильових зауважень, і блокуюча перевірка зупинила б роботу над CRUD. Після PR зі стильовою чисткою ці два рядки прибираються, і порушення починають валити збірку. Проміжний стан зафіксовано коментарями в `pom.xml`, щоб його не забули зняти.

### Запуск

```bash
./mvnw checkstyle:check          # стиль
./mvnw spotbugs:check            # безпека й коректність
./mvnw verify                    # обидва в межах збірки
```

Checkstyle підключений до фази `validate`, SpotBugs — до `verify`.

## 2. Покриття

Аналізом охоплено весь код проєкту: 16 класів у `src/main/java` і 2 тестових класи (`includeTests=true` в обох інструментах). Згенерованого коду немає, зон поза аналізом немає.

## 3. Результати

### Checkstyle: 20 зауважень

| Правило              | Кількість | Приклад                                                      |
| -------------------- | --------- | ------------------------------------------------------------ |
| `LineLength`         | 9         | `OrganizationController.java:57` — 133 символи               |
| `EmptyLineSeparator` | 5         | `OpenApiConfig.java:24` — дві порожні лінії перед класом     |
| `MagicNumber`        | 2         | `GlobalExceptionHandler.java:114` — `16` у довжині requestId |
| `NeedBraces`         | 2         | `GlobalExceptionHandler.java:122,124` — `if` без дужок       |
| `AvoidStarImport`    | 1         | `OrganizationService.java:11` — `java.util.*`                |
| `ConstantName`       | 1         | `GlobalExceptionHandler.java:33` — `log` замість `LOG`       |

Усі 20 — стиль, не дефекти поведінки. Виправляються окремим PR, щоб не змішувати формат із правками по суті.

Виняток: `ConstantName` для `log`. Ім'я `log` для логера — усталена практика в екосистемі Spring, і перейменування на `LOG` зробило б код менш звичним. Варіанти: або прийняти правило й перейменувати, або додати виняток у `checkstyle.xml`. Рішення за командою; поки залишено як зауваження.

### SpotBugs + find-sec-bugs: 13 знахідок

| Категорія        | Тип                                      | Кількість | Рішення           |
| ---------------- | ---------------------------------------- | --------- | ----------------- |
| **SECURITY**     | `SPRING_ENDPOINT`                        | 5         | див. розділ 4     |
| `STYLE`          | `NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE` | 1         | хибне спрацювання |
| `I18N`           | `DM_CONVERT_CASE`                        | 2         | **виправлено**    |
| `MALICIOUS_CODE` | `EI_EXPOSE_REP` / `EI_EXPOSE_REP2`       | 4         | прийнято          |
| `BAD_PRACTICE`   | `SE_BAD_FIELD`                           | 1         | прийнято          |

**`NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE`** у `GlobalExceptionHandler.handleTypeMismatch:70`: аналізатор вважає можливим розіменування результату `ex.getRequiredType()`. У коді перевірка на `null` є (`ex.getRequiredType() == null ? "інший тип" : ...`), тож це хибне спрацювання тернарного оператора. Залишено без придушення: правило корисне, а один шумний випадок не привід його вимикати.

**`EI_EXPOSE_REP` / `EI_EXPOSE_REP2`** у `ApiError` і `OffsetPage`: обидва — Java-рекорди зі списками всередині. Ризик теоретичний, бо списки створюються через `List.of` і `List.copyOf` і є незмінними, але SpotBugs цього не бачить. Прийнято без придушення, щоб правило працювало для майбутніх класів із справді змінним станом.

**`SE_BAD_FIELD`** в `ApiException`: несеріалізовне поле `details` у серіалізовному класі. Винятки в нас ніколи не серіалізуються, тож ризику немає.

### Придушені правила

У `config/quality/spotbugs-exclude.xml` один виняток: `EI_EXPOSE_REP` для класів `*Controller` і `*Service`. Причина — Spring інжектить залежності через конструктор, і збережене посилання на bean аналізатор вважає витоком зовнішнього об'єкта. Кожен виняток має бути обґрунтований у самому файлі: придушене без пояснення правило нічим не краще за невиявлену ваду.

## 4. Задокументована вразливість

**Кінцеві точки запису доступні без автентифікації**

|                  |                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Що**           | `POST`, `PATCH`, `DELETE /api/v1/organizations` виконуються без токена                                                                           |
| **Чим знайдено** | find-sec-bugs, правило `SPRING_ENDPOINT` (категорія SECURITY), 5 входжень у `OrganizationController`                                             |
| **Підтверджено** | ручним запитом: `curl -X DELETE .../organizations/{id}` без заголовка `Authorization` повертає `204`                                             |
| **Загроза**      | **T-02** з [threat-model.md](../architecture/threat-model.md) — Elevation of privilege: будь-хто може створити, змінити або видалити організацію |
| **Оцінка**       | Висока за наслідками, але зараз недосяжна ззовні: сервіс не розгорнутий, працює лише локально на заглушках у пам'яті процесу                     |

`SPRING_ENDPOINT` — інформаційне правило: воно не стверджує, що є вразливість, а каже «цю точку входу треба перевірити вручну». Перевірка показала, що `@SecurityRequirement` у контролері **документує** `bearerAuth`, `401` і `403`, але жодного фільтра автентифікації в застосунку немає. Тобто специфікація обіцяє захист, якого в коді немає — найгірший варіант, бо клієнт і рев'юер бачать у Swagger UI замок і вважають, що все гаразд.

**Рішення: ризик свідомо прийнято на цьому етапі**, з такими умовами:

1. Сервіс не розгортається в публічну мережу, доки немає Auth Module (ADR-002).
2. У `api-design.md` і `quality-attributes.md` зафіксовано, що `401`/`403` наразі перевіряються лише як **контракт**, а не як поведінка.

Цей пункт має бути перевірений першим, щойно з'явиться Auth Module: зараз це єдина знахідка, що безпосередньо відповідає загрозі з моделі загроз.

## 5. Виправлена знахідка з регресійним тестом

**`DM_CONVERT_CASE` — залежний від локалі `toLowerCase()`**

Місця: `ErrorCode.anchor()` і `OpenApiConfig.example()`.

Виклик `name().toLowerCase()` без параметра означає `toLowerCase(Locale.getDefault())`, а типова локаль береться з операційної системи, де запущена JVM. У турецькій локалі `I` переходить у `ı` без крапки, тож `INVALID_PARAMETER` дає якір `ınvalıd-parameter`, і посилання в полі `documentation` кожної помилки веде в нікуди. Ризик для нашого розгортання низький, але клас помилки стає небезпечним, щойно `toLowerCase` з'явиться у звірці ролей чи розширень файлів — тому виправлено одразу.

Явна `Locale.ROOT` в обох місцях — нейтральна локаль без національних правил, саме те, що потрібно для рядків, призначених машині (коди помилок, URL, ключі), а не людині.

Регресійний тест `ErrorCodeAnchorTest` підставляє турецьку локаль і перевіряє якорі. Прогін на коді **до** виправлення:

```
expected: <invalid-parameter> but was: <ınvalıd-parameter>
Tests run: 2, Failures: 1
```

Після виправлення обидва тести проходять. Перевірка «тест справді падає до фіксу» обов'язкова: тест, який ніколи не падав, не доводить нічого — можливо, він перевіряє не те.

## 6. Висновки

**Стан коду прийнятний для поточного етапу.** Жодної знахідки з високим рангом ризику аналізатори не дали: усі 20 зауважень Checkstyle стосуються оформлення, а з 13 знахідок SpotBugs одна виправлена, п'ять зведені до єдиної архітектурної проблеми, решта визнані хибними спрацюваннями або прийняті з обґрунтуванням.

**Головний ризик не в коді, а в розбіжності між кодом і документацією.** Специфікація API оголошує захист кінцевих точок запису, якого в застосунку немає. Для рев'ю це небезпечніше за відверту відсутність автентифікації: у Swagger UI видно замок, і перевіряючий припускає, що все на місці. Розбіжність зафіксована як свідомо прийнятий ризик і закривається разом із Auth Module.

**Цінність аналізаторів на цьому етапі обмежена складом коду.** find-sec-bugs перевіряє передусім SQL-ін'єкції, криптографію й десеріалізацію, а в проєкті поки немає ні бази даних, ні автентифікації — тому більшість його детекторів не має на чому спрацювати. Прогін доведеться повторити після під'єднання PostgreSQL, і саме тоді ці інструменти почнуть приносити основну користь. Єдина виправлена вада (залежний від локалі `toLowerCase`) — показова саме тим, що її неможливо помітити очима під час рев'ю.

**Відкриті дії:** стильова чистка з подальшим перемиканням перевірок у блокуючий режим, рішення команди щодо `ConstantName` для `log`, реалізація фільтра автентифікації й додавання `./mvnw clean verify` у CI.
