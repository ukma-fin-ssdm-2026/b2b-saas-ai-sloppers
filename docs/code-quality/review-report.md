# Code Review: `src/api/main.py`

- **Дата:** 2026-10-09
- **Обсяг:** [src/api/main.py](src/api/main.py) (643 рядки — весь бекенд), [.github/workflows/ci.yml](.github/workflows/ci.yml)
- **Метод:** читання коду; застосунок не запускався, тести не виконувалися

## Підсумок

### 3 сильні сторони

1. **Простота.** Код легко читати: один файл, звичайні функції-обробники, зрозумілі назви, жодних зайвих абстракцій. Щоб зрозуміти, як працює будь-який ендпоінт, достатньо прочитати одну функцію.
2. **Зручність для роботи з ШІ.** Увесь бекенд лежить в одному файлі на 643 рядки, тому асистенту не треба аналізувати весь репозиторій і збирати контекст із десятків модулів — файл повністю вміщується в один запит.
3. **Нормальна документованість для OpenAPI.** Ендпоінти мають описи, моделі запитів і відповідей, задокументовані коди помилок (включно з 401/403), а специфікація генерується з коду окремим скриптом [scripts/generate_openapi.py](scripts/generate_openapi.py).

### 3 пропозиції покращення

Зрозуміло, що це тестовий варіант і від нього не очікується готовність до продакшену, проте:

1. **Поділити код на шари.** HTTP, бізнес-логіка і сховище лежать в одній функції `create_app()`. Варто винести схеми, сервіси й репозиторій в окремі модулі — без цього не вийде ні написати тести, ні перейти на PostgreSQL (A1–A5, структура — у розділі 1).
2. **Вирівняти REST-контракт.** Документ оновлюється через `PUT`, абзац — через `PATCH`; пагінація, ідемпотентність і видалення працюють по-різному для документів і абзаців. Потрібні єдині правила для обох ресурсів (E1, E3–E7, C3).
3. **Додати тести й справжній CI.** Тестів немає, а CI виконує лише `echo "Hello, World!"`. Достатньо тестів через `TestClient` і запуску `pytest` та лінтера в CI (T1, T2).

### 1 потенційна вразливість або ризик

**Гонки даних у сховищі (C1).** Обробники оголошені як звичайні `def`, тому FastAPI виконує їх у пулі потоків, а лічильники id і перевірка ключа ідемпотентності не захищені блокуванням. Два паралельні запити можуть отримати однаковий id або створити два документи з одним ключем — дані мовчки пошкоджуються. Виправлення: блокування навколо операцій зі сховищем (або транзакції після переходу на БД).

### Рекомендована структура

```
src/api/
  main.py            # лише create_app + підключення роутерів
  routers/           # documents.py, paragraphs.py — тільки HTTP
  schemas/           # Pydantic-моделі запитів і відповідей
  services/          # ідемпотентність, кошик, перестановка абзаців
  repositories/      # інтерфейс + in-memory реалізація (потім PostgreSQL)
  domain/            # сутності та доменні винятки (NotFound, Conflict)
```

Сервіси кидають доменні винятки, які один `exception_handler` перетворює на 404/409. Репозиторій передається в роутери через `Depends`.

## 2. Ендпоінти

Усі маршрути мають префікс `/api/v1`.

| Метод і шлях | Що робить | Зауваження |
|---|---|---|
| `POST /documents` | Створює документ, вимагає `Idempotency-Key` | E5 |
| `GET /documents` | Список активних, `limit`/`offset` | — |
| `GET /documents/trash` | Список кошика | E6 |
| `GET /documents/{id}` | Активний документ | E6 |
| `PUT /documents/{id}` | Перейменування | E1 |
| `DELETE /documents/{id}` | М'яке видалення в кошик | E6 |
| `POST /documents/{id}/restore` | Відновлення з кошика | E7 |
| `GET /documents/{id}/paragraphs` | Усі абзаци документа | E3 |
| `POST /documents/{id}/paragraphs` | Додає абзац у кінець або в `position` | E4 |
| `GET /documents/{id}/paragraphs/{pid}` | Один абзац | E2 |
| `PATCH /documents/{id}/paragraphs/{pid}` | Змінює `content` та/або `position` | E2 |
| `DELETE /documents/{id}/paragraphs/{pid}` | Видаляє абзац | E2, E6 |

| № | Проблема | Рекомендація |
|---|---|---|
| E1 | Перейменування зроблене через `PUT`, хоча `DocumentUpdate` містить лише `title`. `PUT` означає повну заміну ресурсу: щойно з'явиться зміна `access_mode`, клієнт буде змушений слати всі поля, інакше «заміна» їх скине. Абзаци при цьому вже оновлюються через `PATCH`. ([main.py:438-455](src/api/main.py#L438-L455)) | `PATCH /documents/{id}` з опційними полями. |
| E2 | Для окремого абзацу `document_id` у шляху надлишковий: id абзаців глобально унікальні (один лічильник `next_paragraph_id`). Це не помилка, а надмірна вкладеність. | Колекцію лишити вкладеною (`/documents/{id}/paragraphs`), елемент зробити пласким (`/paragraphs/{pid}`). Лишити як є теж допустимо: права доступу прив'язані до документа, і з вкладеним шляхом їх перевіряти простіше. |
| E3 | Список абзаців повертається без пагінації, тоді як список документів і кошик її мають. ([main.py:500-505](src/api/main.py#L500-L505)) | Додати `limit`/`offset` або явно задокументувати, що список завжди повний. |
| E4 | Створення абзацу не приймає `Idempotency-Key`, а створення документа його вимагає. Повтор запиту після таймауту створить дублікат абзацу. ([main.py:519-550](src/api/main.py#L519-L550)) | Єдине правило ідемпотентності для всіх `POST`, що створюють ресурс. |
| E5 | Ключі ідемпотентності зберігаються вічно і не прив'язані до користувача. Після появи автентифікації чужий ключ поверне чужий документ. ([main.py:273](src/api/main.py#L273), [main.py:344-352](src/api/main.py#L344-L352)) | Ключ у парі з id користувача, термін життя запису. |
| E6 | Модель кошика неповна: документ із кошика не можна отримати за id, остаточного видалення немає, а абзаци видаляються одразу назавжди, на відміну від документів. | Визначити життєвий цикл: читання документа з кошика, остаточне видалення, політика для абзаців. |
| E7 | Відновлення активного документа повертає 404, хоча документ існує. ([main.py:286-293](src/api/main.py#L286-L293)) | `409 Conflict` для ресурсу в неочікуваному стані. |
| E8 | Усі маршрути, включно з абзацами, мають один тег `documents`. ([main.py:262](src/api/main.py#L262)) | Окремі теги `documents`, `paragraphs`, `trash`. |

## 3. Коректність і надійність

| № | Проблема | Де |
|---|---|---|
| C1 | **Гонки даних.** Обробники оголошені як звичайні `def`, тому FastAPI виконує їх у пулі потоків. `next_document_id += 1`, `next_paragraph_id += 1` і перевірка ключа ідемпотентності за схемою «прочитав — перевірив — записав» не захищені блокуванням. Два паралельні запити можуть отримати однаковий id або створити два документи з одним ключем. | [main.py:342-366](src/api/main.py#L342-L366), [main.py:523-550](src/api/main.py#L523-L550) |
